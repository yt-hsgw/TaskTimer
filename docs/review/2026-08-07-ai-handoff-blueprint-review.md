# AI引き継ぎ資料レビュー

## 対象

- `docs/handoff/tasktimer-blueprint.html`
- `docs/handoff/tasktimer-structure.json`
- `docs/handoff/api-reference.md`
- `typedoc.json`
- TypeScriptのTSDoc互換コメントとRustのrustdocコメント
- READMEのドキュメント導線

## 仕様

TaskTimerの構造、前提、制約、主要ファイル、検証コマンドを、人間向けHTML、AI向けJSON、言語標準に沿った生成APIリファレンスとして保持する。担当AIが変わっても、会話履歴や手書きのAPI一覧へ依存せずプロジェクト全体像を共有できる状態にする。

## 設計理由

既存の設計資料は詳細で正確だが、次の担当者が最初に読むには分散している。HTMLは人が俯瞰するための地図、JSONはAIが構造化して読み込むための索引とする。APIリファレンスはTypeScriptではTypeDoc、Rustでは公式rustdocから生成し、ソースコメントを責務と不変条件の正にする。

## トレードオフ

- 引き継ぎ資料を追加すると更新対象が増える。
- 一方で、構造、制約、主要ファイル、検証コマンドを1か所で把握でき、作業開始時の認識合わせが短くなる。
- 生成物をGit管理しないため、閲覧前に生成コマンドが必要になる。一方で、実装との乖離と巨大な生成差分を避けられる。

## 代替案

READMEにだけ要約を追加する。

不採用理由:

- READMEは外部利用者向け説明も含むため、AI引き継ぎ用の構造データを置くと長くなりすぎる。
- JSONとして読み込む用途に向かない。

手書きのKDoc風リファレンスを併存する案も検討したが、ソースコメントとの二重管理になり、更新漏れを検出しにくいため不採用とする。

## セキュリティ

- 秘密情報、個人情報、ローカルDBパスは含めない。
- 外部通信なし、ユーザー本文ログ出力禁止、HTML描画禁止、通知本文のプライバシー境界を明記する。

## 破綻シナリオ

- 実装変更後にJSON/HTMLが更新されず、次のAIが古い構造を正として作業する。
- API変更時にソースコメントが更新されず、生成リファレンスの説明だけが古くなる。
- TypeDocまたはrustdocの更新でCI上だけ生成に失敗する。
- 予定期間と期限の違いが引き継がれず、通知ルールを誤更新する。
- UI変更時に全体再描画やちらつきの制約が見落とされる。

## 受け入れ条件

- HTMLをブラウザで開けば全体像が分かる。
- JSONが構文として妥当で、主要レイヤー、主要ファイル、Use Case、制約、検証コマンドを含む。
- `npm run docs` でTypeDocのHTML/JSONとrustdocのHTMLを生成できる。
- 主要UI、Use Case、SQLite、通知、タイマー境界の責務と不変条件がソースコメントにある。
- CIでAPIリファレンスを生成し、壊れたリンクを失敗として検出する。
- READMEから3種類の引き継ぎ資料に到達できる。
